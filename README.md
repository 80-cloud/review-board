# review-board

成長支援型のレビューコミュニティアプリ。投稿に対して**多軸評価＋コメント＋合格バッジ**で建設的なフィードバックを返す、IT 未経験の学習者向けの相互レビュー基盤です。

**ライブデモ**：https://review-board-jp.duckdns.org/ （登録不要・ログイン画面のデモアカウントで全機能を試せます）

> とくに力を入れた領域：**セキュリティ・認可**。設計判断の根拠は [docs/要件定義書.md](./docs/要件定義書.md) と [docs/品質判定表.md](./docs/品質判定表.md) を参照。

## なぜ必要か

学習者どうしが作品を見せ合い、観点別の評価とコメントで成長を積み重ねられる場をつくりたいと考えました。人のデータと権限を扱うサービスなので、機能を増やすことより先に **認証・認可・セキュリティを「本番で通用する品質」で作る**ことを主眼に置いています。

## 主要機能

- **作品投稿とレビュー**：投稿に対して多軸評価・コメント・合格バッジを返す。
- **成長の可視化**：受け取った評価やバッジの積み重ねを成長記録として表示。
- **認証**：JWT をアクセス用／リフレッシュ用の 2 段構成にし、多要素認証（TOTP）とリカバリコードに対応。
- **認可**：ロールとコホート（受講期）の境界で、「見えない＝404 / できない＝403」を全 API で統一。
- **監査ログ**：操作履歴をハッシュでつないで記録し、改ざんを検知できる。
- **画像アップロード**：ファイルの実体（マジックバイト）で検証し、署名付き URL で配信。
- **全文検索**：PostgreSQL の索引（pg_trgm）で投稿を検索。

## 強み

- **一貫した認可設計（見えない＝404 / できない＝403）**：権限外のリソースは存在ごと隠して 404、権限はあるが操作できないものは 403 と全 API で統一。ID 直指定の攻撃（IDOR）を設計段階で塞ぐ。判定はサービス層に集約。
- **多層の認証・セッション保護**：JWT の 2 段構成、Cookie は Secure / HttpOnly / SameSite=Strict、TOTP による多要素認証。リフレッシュトークンはローテーションと盗用検知に対応。
- **監査ログの改ざん検知**：操作履歴をハッシュチェーンで記録し、後からの書き換えを検証できる。
- **アップロードの安全対策**：拡張子でなくファイルの実体で判定し、保存先でも隔離する。
- **IaC と自動デプロイ（本番稼働まで到達）**：Terraform で AWS（EC2 / S3 / RDS）へデプロイし、正規 TLS（Let's Encrypt）で稼働中。GitHub Actions でビルド→配信→デプロイを自動化し、誤操作の歯止めも複数用意。
- **品質の作り込み**：結合テストと負荷テストを CI で継続実行し、アクセシビリティは Lighthouse 全ページ 100。

## ローカル起動

```bash
# ① DB + MinIO（Docker）
cd review-board
docker-compose up -d

# ② バックエンド（Spring Boot）
cd backend && ./gradlew bootRun

# ③ フロントエンド（Vite）
cd frontend && npm install && npm run dev
# → http://localhost:5175
```

ポートは固定運用（競合時は使用中のプロセスを停止してから正規ポートで起動する）。

## 達成度と今後強化する論点

個人開発・AWS 無料枠を前提に、まず品質の核（セキュリティ・認可・保守性・性能）を作り込みました。可用性の冗長化は、必要になった段階で有効化する前提で、意図的にスコープを絞っています。

- **セキュリティ・認可**：多層防御・認可マトリクス・監査ログのハッシュチェーン・MFA（TOTP）・リカバリコードを実装。
- **保守性**：CI の Fail Fast、通し E2E（smoke + アクセシビリティ）。
- **性能・UX**：性能目標値を定義し実測で達成、アクセシビリティは Lighthouse 全ページ 100。
- **安定性**：AWS への本番デプロイを実証（正規 TLS・CD 自動化）。冗長化（Multi-AZ・ALB・Auto Scaling）とクロスアカウントバックアップは、本格運用の段階で有効化する論点として整理。

詳細は [docs/品質判定表.md](./docs/品質判定表.md)。

## AI の活用方針

設計・実装・レビュー・ドキュメント作成の各工程で、AI コーディングツールを活用しています。使い方の方針を明確にしておきます。

- **設計判断と最終責任は自分が持つ**：AI の提案はそのまま採用せず、意図と根拠を理解したうえでレビューして取り込んでいます。
- **動作は必ず自分で検証する**：テスト・実機確認・CI のグリーンを確認してからマージしています。
- **道具として使いこなす**：AI を開発を速める道具と位置づけ、品質と成果物の責任は自分にあります。
