# テスト計画

> テストは「安心して変更するための仕組み」です。
> 自動でチェックが走るので、間違いがあっても本番に出る前に気づけます。
> このページでは、どんなテストを・なぜ・どこで行うかを、やさしく説明します。

## 1. 目的

- 機能が期待どおり動くことを確かめる
- とくに「だれが・何にアクセスできるか」（権限）が守られていることを確かめる
- 変更のたびに自動で検査し、こわれた状態が本番に出るのを防ぐ

## 2. テストの種類

| 種類 | 何を見る | たとえ |
|---|---|---|
| 単体テスト | 小さな部品が正しく動くか | 1つの計算が合っているか |
| 結合テスト | 部品をつないで動くか（DB なども含めて） | API を呼ぶと正しく保存・取得されるか |
| E2E（通し）テスト | 画面から操作した一連の流れ | ログイン→投稿→表示が通るか |
| 性能テスト | たくさんアクセスしても十分速いか | 同時アクセス時の応答時間 |
| セキュリティ検査 | 弱点や機密の漏れがないか | 古い部品の脆弱性、秘密の混入 |

## 3. いちばん大事にしているテスト：権限の確認

このサービスの肝は「他人や他クラスの情報にアクセスできないこと」です。
そこで、**正しく使える（できる）** だけでなく、**できてはいけないことが本当にできない（拒否される）** ことも必ずテストします。

権限テストの例：

- 他人の投稿は編集・削除できない（できたら不合格）
- 別のクラスの投稿・成長記録は見えない
- 受講生は「最終評価（合格/差し戻し）」をできない（講師だけ）
- ログインしていないと保護された API は使えない

> 「できないことを確かめる」テストがあるのがポイントです。

## 4. セキュリティの自動検査

毎回の変更で、次を自動でチェックします。

- **依存パッケージの脆弱性スキャン**：使っている部品に既知の弱点が無いか
- **機密情報スキャン**：パスワードや鍵をうっかりコードに含めていないか
- **コードの静的解析（SAST）**：危険なコードのパターンが無いか
- **部品一覧（SBOM）の作成**：何を使っているかを記録（後から弱点を追える）

## 5. 画面での確認（E2E・手動）

- 自動の E2E で、ログインや主要画面が表示されることを確認します。
- 大事な機能は、実際のブラウザでも目視で動作を確認します（画面崩れやエラーの有無）。

## 6. いつ走るか（CI）

- 変更を提案（プルリクエスト）するたびに、上のテストが**自動で実行**されます。
- すべて通らないと取り込まないのが基本方針です。
- 性能テストは「この速さを下回ったら不合格」というしきい値で合否を決めます。

## 7. カバレッジ（どれだけ網羅したか）の方針

- 学習段階では、カバレッジ率での合否のゲートは設けていません。
- ただし数値は参考として把握し、足りない所を見つける手がかりにします。
- 本格運用に移る際に、ゲートの導入を検討します。

## まとめ

- 「できる」だけでなく「できてはいけないことが拒否される」を必ずテスト
- セキュリティ検査（脆弱性・機密・静的解析・部品一覧）を自動で常設
- 変更のたびに CI で自動実行し、通らないものは取り込まない
