# デプロイとロールバックの手順

> 「デプロイ」＝新しいバージョンを本番サーバーに反映すること。
> 「ロールバック」＝うまくいかなかったときに前のバージョンへ戻すこと。
> このページは、その2つを安全に行うための流れを、なるべくやさしく説明します。

## 大事な考え方：ビルドと反映を分ける

新しいコードをいきなり本番に反映すると、失敗したときに戻しづらくなります。
そこで2段階に分けています。

1. **ビルド（梱包）**：コードから「動く一式（成果物）」を作り、置き場（クラウドのストレージ）に保管する。
   - このとき、変更を識別する短い番号（コミットの SHA）を名前に付けて保存します。
   - 同じ番号の成果物は中身が変わらない（＝あとで同じものを再現できる）ようにします。
2. **反映（昇格）**：保管した成果物のうち「どれを本番に出すか」を、人が選んで反映する。
   - 自動で勝手に本番へ出さず、必ず人の操作（承認）を挟みます。

この「梱包」と「反映」を分けることで、戻したいときは保管済みの前の成果物を選ぶだけで戻せます。

## サーバー上の置き方

本番サーバーでは、バージョンごとにフォルダを分けて置き、
「いま使う版」を指すショートカット（シンボリックリンク）を切り替える方式にしています。

```
releases/
  <新しい版>/   ← 今回反映する版
  <前の版>/     ← 1つ前（戻すときに使う）
current  ->  releases/<いま使う版>   ← ここを切り替えるだけで版が変わる
```

切り替え後にアプリを再起動すれば、新しい版で動き始めます。
データベースの構造変更（マイグレーション）は、アプリ起動時に自動で適用されます。

## デプロイ（反映）の流れ

1. 変更をメインのブランチに取り込む（レビュー済みのコードのみ）。
2. **ビルド**を実行し、成果物がストレージに保存され「成功」になるのを確認する。
3. 反映したい版の短い番号（SHA）を確認する。
4. **反映**を、番号と「実行する」の確認入力を添えて手動で実行する。
5. 反映後、サーバーが「健康（応答 OK）」かを確認する。

> ポイント：「メインに取り込む＝本番反映」ではありません。反映は必ず別の手動操作です。

## ロールバック（前に戻す）

### いちばん簡単：前の版をもう一度反映する

前の版の番号（SHA）で、デプロイと同じ「反映」を実行するだけです。
保管済みの成果物を選び直すイメージなので、すぐ戻せます。

### 緊急時：サーバー上で手動で切り替える

サーバーに安全な経路で入り、`current` のショートカットを前の版に向け直して再起動します。
（普段は使いません。自動の経路が使えないときの最終手段です。）

## つまずきやすい点

- ビルドが成功していない番号は反映しないこと（中身が無いと失敗します）。
- 反映の前に、サーバー（アプリ・データベース）が起動しているか確認すること。
- 反映するとデータベースの構造変更が走ります。基本は「列の追加」など影響の小さい変更ですが、内容は事前に把握しておきましょう。

## まとめ

- ビルド（梱包）と反映（昇格）を分ける。
- 反映は人が承認して行う。
- 戻すときは前の版を選び直すだけ。
- 反映後は必ず健康チェック。
