# インフラ構成

> 「インフラ」とは、アプリを動かす土台（サーバーやデータベースなど）のことです。
> このページでは、どんな部品をどう組み合わせて本番を動かしているかを、やさしく説明します。

## 1. 全体像

```
[ブラウザ]
   │  HTTPS（暗号化通信）
   ▼
[受付（nginx）]  ── 静的ファイルの配信 ＋ アプリへの取次ぎ
   │
   ▼
[アプリ（Spring Boot）]
   ├─▶ [データベース（PostgreSQL）]   … 投稿・レビュー・ユーザーなど
   └─▶ [画像ストレージ（S3 互換）]     … スクリーンショット（非公開・一時URLで配信）
```

## 2. 使っているクラウドの部品

| 部品 | 役割 |
|---|---|
| 計算サーバー（EC2 相当） | アプリと受付（nginx）を動かす |
| データベース（マネージド DB / RDS） | データを保管。バックアップや運用をクラウドに任せる |
| 画像ストレージ（オブジェクトストレージ / S3） | スクリーンショットを保管（非公開） |
| 予算アラート | 想定外の課金に早く気づくための見張り |
| 構成管理（Terraform） | サーバー構成を「コード」で定義し、再現できるようにする |

## 3. ネットワークの考え方

- **データベースは外から直接アクセスできない場所（プライベート）**に置きます。アプリ経由でしか触れません。
- サーバーへの管理アクセス（保守用の入口）は、必要な範囲だけに限定します。
- 外に開けるのは Web の入口（HTTP/HTTPS）など、必要な口だけにします。

## 4. 安全のための多層の工夫

ひとつの対策に頼らず、層を重ねます。

- 通信は HTTPS で暗号化
- ログイン情報の Cookie は安全な設定（外部サイトから使われない・盗まれにくい）
- スクリーンショットは**非公開**で保管し、見るときだけ**短時間で切れる URL**を発行
- アプリには必要最小限の権限だけを与える（最小権限）
- パスワードや鍵などの機密は**コードに書かず**、安全な保管場所から渡す

## 5. 運用の流れ

- **構築**：サーバー構成はコード（IaC）で定義。手作業を減らし、同じ環境を再現できる。
- **コスト節約**：使わない期間はサーバー/DB を止めて課金を抑えられる。
- **日常**：新しい版の反映は「ビルド → 手動で承認して反映」（別ドキュメント参照）。

## 6. コストの方針

- 無料枠を中心に、低コストで運用することを基本にしています。
- 予算アラートで、想定を超える課金に早めに気づけるようにしています。

## 7. 誤操作を防ぐしくみ

クラウドの操作ミスは取り返しがつかないことがあります。そこで、

- 重要な資源（データベースなど）は**簡単には消せない設定**にする（削除保護）
- 削除・作り直しのような**取り返しのつかない操作は、人の確認を必ず挟む**
- 構成変更はコードのレビューを通してから反映する

といった「うっかり」を防ぐ仕組みを重ねています。

## 8. いまは簡素にしている点（今後の課題）

- サーバーは1台構成（冗長化・自動切替は今後の課題）。
- 学習段階のため、大規模運用向けの追加部品（前段の防御層など）は最小限。
- これらは本格運用に移る際に見直します。

## まとめ

- ブラウザ → 受付 → アプリ → DB / 画像ストレージ、という素直な構成
- DB は非公開、画像も非公開＋一時 URL、通信は暗号化
- 構成はコード化し、誤操作は「消せない設定」＋「人の確認」で防ぐ
