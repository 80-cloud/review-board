## このドキュメントの目的

化粧直し完了時点で review-board は **3 位（slack-board と入れ替わり）** に到達している想定。ここから **TripDiary・sns-board を抜いて単独 1 位** を狙うために必要な「もう一段」の作業を、**ROI（効果/工数）順** に並べて引き継ぐ。

設計と文書では既に 1 位の射程にいるため、本書の作業は **「実装をドキュメントに追いつかせる」** フェーズと位置づける。

## 全体方針

```
1〜3 (2 日)  : 触り心地の完成 → TripDiary に並ぶ
─────────────────────────────────────────
4〜7 (5 日)  : 数字と実装の厚み → sns-board を抜く
─────────────────────────────────────────
合計 7 日   : 単独 1 位を狙える
```

各タスクは独立しているため複数人で並行可能。ただし **#4（品質判定表 N/A → A 化）は他のタスクと連動**するので、#1〜#3 を終えた後に開始するのが望ましい。

# 1. シードデータ + デモアカウント

## なぜ必要か

- **第三者評価者は「触って 30 秒」で完成度を判定する**。空のデータベースにログインして真っ白な画面が出ると、その時点で評価が止まる
- TripDiary が 1 位だった理由の一つは「画面に旅行記録が並んでいる証拠」。review-board は機能数が多い分、データが空だと寂しさが倍増する
- 公開 URL を持っていても、デモアカウントが無いと「アカウント作るのが面倒」で離脱される
- 重点領域の S 級セキュリティを保つために、デモアカウントは **デモ用権限のみ**（投稿は全部削除可、他人の投稿は触れない、本番ロールではない）にする必要あり

- 現状 V1〜V23 まで本番スキーマ。**V24__seed_demo_data.sql は別 location** に置く
- パス: [backend/src/main/resources/db/seed/V24__seed_demo_data.sql](review-board/backend/src/main/resources/db/seed/V24__seed_demo_data.sql)
- `application.yml` で `spring.flyway.locations` を `classpath:db/migration` のみ（本番）/ `classpath:db/migration,classpath:db/seed` （demo profile）と分岐
- これにより本番 RDS にデモデータが流れる事故を防ぐ

### 1-2. シードデータ内容
- ユーザ 5 名（demo1〜demo5、それぞれ性格の違うペルソナ）
- 投稿 20 件（各ユーザ 4 件ずつ、AI 使用フラグ / 公開範囲 / カテゴリをばらす）

### 1-3. デモアカウント
- `demo@example.com / Demo1234!`（README 冒頭と LoginPage に表示）
- パスワードは Argon2 でハッシュ化（本番ユーザと同じ仕組み）
- ロール: `DEMO`（新規追加、`USER` から削除権限・招待権限を制限）

### 1-4. ログイン画面に「デモで試す」ボタン

# 4. 品質判定表 N/A → A 化（実装伴う分）

## なぜ必要か

- review-board の **最大の競争優位は「自己採点フレームワーク（[品質判定表](review-board/docs/品質判定表.md)）」を持っていること**
- ただし「自己採点」のままだと第三者からの説得力が弱い
- N/A や 対象外（簡素化） を 1 つずつ **実装で A 化** することで、品質判定表が「絵に描いた餅」から **「実装の進捗計器」** に格上げされる
- これは他アプリ（TripDiary / sns-board）には無い独自ポジション。**ここを磨くと「数字では sns-board に並び、設計では独走」** という構図になる
- 「自己採点を実装で証明している」という事実そのものが、品質に対する取り組み姿勢の証拠になる

## やること

### 4-1. 現状棚卸し
- [docs/品質判定表.md](review-board/docs/品質判定表.md) を開き、`N/A` / `要改善` / `対象外（簡素化）` のセルを全てリストアップ
- Spreadsheet にコピー（Issue とのリンク用）

### 4-2. 実装で潰せる SHOULD を選別
以下は **#5〜#7 の作業で同時に A 化できるもの**：

| 要件 ID（推定） | 内容 | 連動するタスク |
|---|---|---|
| M-9 構造化ログ | Logback の JSON 出力確認 | #6 と同時 |
| M-10 メトリクス | Spring Boot Actuator `/metrics` 公開 | #6 と同時 |
| M-13 実ブラウザ検証 | E2E 8〜10 本で A 化 | #5 で完了 |
| S-1 監視・通知 | CloudWatch アラーム | #6 で完了 |
| P-2 ページネーション | 既存実装の確認 / cursor 化 | 単独 |
| P-9 a11y 全ページ | Empty State + 404 でも 100 | #2 で完了 |
| SEC-7 監査ログ | `audit` ドメイン実装状況確認 | 単独（既に A の可能性） |

### 4-3. 純粋に実装が必要な項目
他タスクと連動しない項目（例：`P-2 cursor ページネーション`）は **1 PR 1 項目** で着実に消す。

### 4-4. 品質判定表の同期更新
- 各 A 化 PR で `docs/品質判定表.md` の該当行を同時更新
- 更新ルール: `判定` 列を A に、`根拠・備考` 列に PR 番号と実装ファイルパスを記載

## 完了判定
- [ ] 純粋未達 MUST が **0 件**（既に達成済の想定。再確認のみ）
- [ ] N/A の SHOULD が **半分以下** に減る
- [ ] 品質判定表の「正直な現状認識」セクションが更新される
- [ ] 残った N/A / 対象外は **「あえて簡素化」** の理由が明記される

## 想定工数
1〜2 日

## 注意点
- **無料枠の制約であえて簡素化しているもの**（Multi-AZ / クロスアカウントバックアップ）は **A 化を狙わない**。コストが見合わない
- 「対象外（簡素化）」を残す場合は、**理由を品質判定表に明記**することで「逃げ」ではなく「設計判断」として説明できる
- ADR を併せて起こすと、判断の経緯が残って将来の見直しがしやすい

# 6. CloudWatch アラーム + 通知配線

- これは品質判定表の「設計書と実装の乖離」として最も指摘されやすい弱点
- 安定性軸 S を補強する最短ルート
- 「実際にアラームが鳴って通知が届く」サイクルを 1 回でも回せれば、運用品質の証拠として強い

## やること

### 6-1. インフラ実装

### 6-2. 必須メトリクス（5 つ）

| メトリクス | 閾値 | 評価期間 | 重要度 |
|---|---|---|---|
| ALB 5xx エラー率 | > 1% | 5 分 | 高 |
| ECS タスク健全性 | running < desired | 1 分 | 高 |
| RDS CPU 使用率 | > 80% | 5 分 | 中 |
| RDS FreeStorageSpace | < 1 GB | 5 分 | 中 |
| アプリログ ERROR 発生 | > 0 | 1 分 | 高 |

### 6-3. 通知配線
- SNS トピック作成 → メール購読（個人メールアドレスは Terraform variables で受け取り、tfvars 非コミット）

### 6-5. 設計書との対応表
